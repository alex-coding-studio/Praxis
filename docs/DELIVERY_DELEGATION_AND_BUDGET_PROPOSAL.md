# 交付委派与运行预算方案

状态：用户讨论稿，尚未实施。本文用于确认产品行为，不是当前 Agent 的运行指令。

## 任务摘要

为 Praxis 开发交付增加“一层委派＋统一运行预算”：Orchestrator 统一管理 Agent 分配，Worker 和 Reviewer 保留任务内自主性，但不能继续向下委派；Host 为一次用户发起的交付运行累计时间、用量和委派次数，达到上限后可恢复地暂停。用户明确继续才能追加额度，不允许 Agent 通过新建 session、切换模型或自动重启来重置预算。

先实现委派边界与可见计数，再实现预算、暂停和继续。当前正在运行的任务不追溯应用新限制。本文中的默认数值是试运行起点，需要根据真实任务校准，不代表质量或完成时间承诺。

## 1. 要解决的问题

- Worker 嵌套派发可能使模型调用数、成本和工作区写入关系失去控制。
- 无限对话或持续重试缺少统一的停止边界。
- 各 provider 的 turn 定义和暂停／恢复机制不同，不能直接套用同一个 max-turns 数字。
- 预算保护不能再次变成“固定 repair 次数用尽，所以整个任务失败”，也不能丢弃已完成的代码和证据。

## 2. 委派关系

```text
用户 → Orchestrator → Worker / Reviewer
```

- 只有 Orchestrator 可以创建 assignment、选择配置池内的模型、升级模型和安排并发。
- Worker 和 Reviewer 不提供 Praxis 委派工具，并关闭对应 provider 的原生子 Agent 能力。
- Worker 需要帮助时，说明具体问题、已完成内容和需要的能力，由 Orchestrator 决定续做、换模型或增派；提出协作需求本身不算任务失败。
- 不允许通过 Bash 另起模型进程来绕过委派管理。正常读取、搜索、编辑、构建、测试和任务内修复仍然允许，不扩大为命令白名单。
- 这是可信 Agent 的成本与组织治理，不宣称能靠提示词和工具隐藏实现对任意恶意进程的安全隔离。若 provider 无法真正关闭原生委派，适配器必须明确报告该限制。
- 同一 worktree 同时只能有一个写入者。当前先沿用顺序实施；并行写入必须先有独立 worktree 支持。只读 Reviewer 不得与正在改变被审查 HEAD 的写入任务混用同一验证快照。

当前代码观察：Claude 原生工具列表没有 Agent／Task，Praxis 的 dispatch_agent 不给 Worker；Codex 的 explicitRequestOnly 不等于禁止嵌套委派。实施时重新验证各 provider 的实际工具面，不能以提示词作为唯一证明。

## 3. 预算归属与计数

预算属于一次用户发起的 Delivery Run。它覆盖 Orchestrator 和该 Run 下所有 assignment，不能只限制某一次 CLI 进程。

- Target：持续的交付对象，可以包含多次用户沟通和执行 Run。
- Run：一次用户明确触发的执行／反馈运行，是总预算归属单位。
- Assignment：Orchestrator 指派给 Worker 或 Reviewer 的具体工作。
- Provider turn：provider 自己定义的调用单位，必须由适配器说明其含义，不直接等同于 Run 或工具调用次数。

同一 assignment 因 Host job、工具结果或 session 恢复而继续，不增加 assignment 数量，也不清零其预算。更换承担该工作的 session 或模型，仍归入原 assignment；另起一个 assignment 则消耗本轮的新增委派额度。

预算及计数需要持久化。Host 重启后仍能恢复已消耗量；无法确认旧进程是否停止时，不启动另一个写入链。

## 4. 第一版试运行默认值

| 范围                      | 提醒点  | 暂停上限 |
| ------------------------- | ------- | -------- |
| Orchestrator 自身活动时间 | 10 分钟 | 20 分钟  |
| 单个 Worker assignment    | 20 分钟 | 45 分钟  |
| 单个 Reviewer assignment  | 10 分钟 | 20 分钟  |
| 整个用户发起的 Run        | 45 分钟 | 60 分钟  |

Orchestrator 自身活动时间排除等待 Worker／Reviewer 的区间，但包含其直接处理任务、等待模型和自身工具执行的时间。Assignment 时间包含该 assignment 的模型及工具等待。整轮时间按运行中的墙钟时间累计，并发区间只计一次；用户暂停后等待继续的时间不消耗活动预算。

单轮最多启动 8 次 Worker／Reviewer assignment，所有角色合并计数。恢复既有 assignment 不计新增。初始化时保存预算快照，设置变更只影响后续 Run；当前 Run 只能通过用户明确追加额度来改变上限。

提醒点不是暂停点：只更新 UI 和日志，不额外启动模型总结，也不把运行状态改为 Warning。用户仍可随时主动取消。

## 5. 达到上限后的行为

1. Host 停止接受新的委派和新工具执行请求。
2. 中断模型继续生成，并取消可取消的工具；对已经提交的外部操作和不可立即停止的发布步骤等待明确结果。沿用现有 Host operation drain，不能一边发布一边清理工作区。
3. 持久化当前进度、工作区、提交、PR、session、已取得证据以及停止原因。
4. 显示 Warning：“本轮运行额度已用尽”，与代码错误、认证失败和用户撤销区分。
5. 展示额度种类、已用量、当前角色、最后活动和日志入口。

预算上限是停止继续工作的边界，不承诺外部命令在同一毫秒全部终止。尚未停止时显示“正在停止”，不提前开放继续或新的写入操作。若无法确认停止，明确显示该情况并保留现场。

优先采用 Agent 已有的总结，不为了获得总结额外开启一轮不受限调用。没有总结时由 Host 提供上述事实摘要。

单个 assignment 用尽额度后，先暂停该 assignment 并通知 Orchestrator。Orchestrator 可以在剩余整轮预算内汇总和说明下一步，但不能自动为同一项已用尽额度的工作换一个 assignment 续命；继续该工作需要用户追加额度。整轮或 Orchestrator 额度用尽则暂停整条执行链。

## 6. 用户继续与撤销

- “继续”明确显示将追加多少额度以及适用范围，用户确认后才恢复。
- 保留原 Run 的预算历史，不把已用量改为零；恢复同一 Target、工作区、PR 和可用 session。
- 不能通过自动新建 Run、换模型、换 session 或重复 dispatch 绕过暂停。
- “撤销本次交付”继续使用已有撤销规则；预算暂停本身不删除代码、关闭 PR或撤销交付。
- 这套限制不增加固定 repair 次数。一次自然的编译／测试修复按真实消耗计入预算，不单独消耗所谓“修复名额”。

## 7. Turn 与 token 的后续接入

第一版先用时间和 assignment 数量提供跨 provider 的有效边界，同时展示可取得的 token 数据。

逐一确认 Claude、Codex 和其他 provider 的原生 turn 定义、限制入口、恢复行为和终止事件，再引入适配器级 turn 上限。没有可靠计数时显示“不可用”，不能把它计为零或声称已经限制。

Token 统计要求：

- 区分输入、缓存输入、非缓存输入和输出；reasoning 子项不能重复相加。
- 分清单次调用增量和累计快照，避免重复计数。
- 汇总所有角色，覆盖暂停、恢复和模型切换。
- 缓存 token 不能直接按非缓存 token 视为等价成本。
- 套餐额度和 API 金额没有可靠映射时，只报告实际 token，不伪造费用估算。

在计量经过验证之前，不启用统一 token 硬预算，也不先写一个跨 provider 的 maxTurns 常量。时间上限先负责兜底。

## 8. UI 与日志

- 模型配置中提供模块级默认预算配置；不要在输入区增加一排常驻控制。
- Sticky Header 保留状态和耗时；预算详情通过紧凑入口查看，不重复显示长篇 Agent 回复。
- 预算暂停时，顶部给出明确标题、简短原因、日志和“继续”动作。主要动作仍位于次要动作下方。
- 日志区分 HOST、ORCHESTRATOR、WORKER、REVIEWER，记录委派、模型选择、预算提醒、停止、追加及恢复。
- 长时间没有工具事件本身不构成 Warning；判断基于实际预算状态，不靠猜测 Agent 是否在思考。

## 9. 实施顺序与验收

### 第一阶段：委派边界和可见计数

- 对齐各 provider 创建与恢复时的工具能力，保证 Worker／Reviewer 不获得委派入口。
- Orchestrator 的委派入口统一检查角色、模型池、写入归属和 assignment 额度。
- 建立持久预算账本，先显示真实耗时、委派次数和可用的 token 统计，不启用未经校准的 token 上限。

验收：Worker 的直接委派被拒绝；合法请求由 Orchestrator 处理；恢复同一 assignment 不重计；不同 Target 的账本互不串扰；原有读取、实现和修复能力仍可用。

### 第二阶段：暂停与继续

- 接入提醒点、停止边界、运行中 UI、Host 日志和用户追加额度。
- 覆盖 provider 中断、Host 工具排空、外部发布未结束和服务重启后的恢复。

验收：达到预算后不再派新工作；暂停保留代码／PR／证据；发布未结束时不提前允许并发恢复；用户继续追加额度而非清零；切换 session 不绕过预算；长时间没有工具活动但预算未到时保持运行态。

使用可控时钟、模拟 provider 和既有临时 Git fixture 验证这些真实边界。不为测试消耗实际模型额度，不做 mutation、不重复无关 gate，不为所有低概率假设增加防御流程。

## 10. 范围外

- 不改变 Delivery Brief、Target 或 PR 的粒度。
- 不强迫每个任务创建 Worker，也不使 Reviewer 成为必经步骤。
- 不重建 Agent 权限白名单或固定 repair 轮数。
- 不新增计费系统或跨 provider 的虚构成本换算。
- 不追溯中断已经在运行的任务。
